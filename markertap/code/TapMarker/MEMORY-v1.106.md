# 新しい回路へ処理を組み直す場合のメモリ削減余地

既存BANC回路の抽出ではなく、画面取得・認識・判断・入力の処理を新しいノードと接続へ組み直す案に対する、現行版の基準値です。新方式は未実装で、削減率は測定していません。

## 現行版のモデル測定

OpenJDK 17のInstrumentation.getObjectSizeを使用し、同じオブジェクトを重複しないよう探索しました。標準設定をruntimeCopyしたエンジン、AdaptiveLayout、UpgradeEngineの到達可能オブジェクトを対象とし、静的メタデータ、Android側の画面・プロセス、観測後の一時配列、学習済み記憶は含めません。画像見本は長さ768以上のfloat配列として別集計しています。

| 対象 | 合計 | 画像見本以外 |
|---|---:|---:|
| 増えうさぎのエンジン・レイアウト・強化処理 | 632,096 bytes | 83,264 bytes |
| 農園うさぎの同対象 | 314,312 bytes | 43,064 bytes |
| 個別測定の合計 | 946,408 bytes | 126,328 bytes ≒ 0.12MiB |

これはAndroidのPSSや実機での使用RAMではありません。オブジェクト配置はARTと異なり、アプリ間の共通オブジェクトが合計に重複する場合もあります。「画像見本以外」も制御データ全体を完全に分離したものではありません。その全量を新方式へ置き換えても、この初期モデルでは約0.12MiBが上限の目安です。新方式自身のデータも必要になります。

測定補助は `tools/memory-probe/HeapAgent.java` と `MemoryFootprintProbe.java` です。ビルド済みclassfile runtime、既存テストの読込補助、`tests/current-layout-evidence.bin` 等を使用します。Java agentとして実行し、java.base/java.langとjava.base/java.utilの参照を許可して測定します。

## 画像の保持方法まで変える場合

現行の各Windowは元画像latestと解析用snapshotのint配列を持ちます。両方が確保された後の要素データは、画素数×4 bytes×2配列です。2画面の設定例では次の計算です。

| 1画面の画素数 | 2画面・各2配列の合計 |
|---|---:|
| 540×1212 | 10,471,680 bytes ≒ 9.99MiB |
| 720×1616 | 18,616,320 bytes ≒ 17.75MiB |

これらは実機の設定値や実測値ではなく、軽量・標準モードに相当する解像度の例です。配列ヘッダ、ImageReader/gralloc/GPU、ゲーム本体、サムネイル、解析中の一時データは別です。

新しい回路が必要な領域の特徴量だけを出力し、不要なフルフレーム保持・複製を廃止できるなら、この10～18MiBの一部が削減対象になります。全配列を廃止する場合でも、入力フレームの参照寿命、広告終了印の全体探索、色変換、同時入力、プレビュー表示、古い画像の排除を保つ必要があります。別の同サイズバッファへ移しただけなら削減になりません。ゲーム本体のメモリは別に残ります。

回路化という表現形式だけで圧縮は保証されません。接続数・状態量を増やせば逆に増えます。同じ録画、同じ画面判定・入力結果を維持した通常実装と新方式について、実機のピークPSS、Java/native/graphicsの内訳、CPU時間、CM後の継続を比較する必要があります。
