# MarkerTap v1.109 起動解像度の実験版

仮想画面の作成時に使う画素数を段階的に下げ、アプリごとに表示・認識・タップが成立する幅を探します。プレビューを小さくする設定とは別です。

## インストールと開始

1. 旧版で「全停止」を押し、`MarkerTap-v1.109-resolution-lab.apk` を上書きインストールします。従来と同じパッケージ・証明書で署名しています。
2. 「設定」→「仮想画面の起動解像度」→「起動解像度の実験」を開きます。
3. 最初は「自動（従来設定）」で対象アプリを開き、普段の動作を確かめます。
4. 実験画面で「動作結果を記録」から、各アプリの結果を保存します。
5. 「一段下げる（次回起動）」→「選択した幅で開き直す」を押します。旧画面を閉じた後、新しい画面を作ります。
6. 作り直した画面は自律停止の状態です。表示を確認してからホームの「自動開始」で認識・タップを試し、各アプリの結果を記録します。

旧実行部が残ったという表示が出たら「端末だけで接続」から実行部を起動し直してください。今回の実行部は小さい解像度と低DPIに対応する revision 90 です。

幅の選択を保存しただけでは、稼働中の画面の解像度は変わりません。開いている画面がない場合は、ホームから対象アプリを選んで開くと保存した幅が適用されます。「自動開始」だけでは既存画面の解像度は変わりません。

## 実験の進め方

選択肢は、自動／720／640／540／480／400／360／320／280／240／200／160／128／96／64／48／32pxです。高さは元画面の比率に従い、明示した幅ではDPIも同じ縮小率で計算します。整数への丸めがあるため、特に極端に小さいDPIでは論理上の表示サイズに誤差が出ます。通常設定の既存の72dpi下限は「自動」で維持します。

- 最初は同じ2アプリ、同じ負荷設定、同じ場面で比較します。画面数・認識間隔・タップ設定を同時に変えると原因を切り分けにくくなります。
- 基準→540→480→400→360→320と順に試し、その後は280・240・200・160も個別に確認します。基準が540pxなら次は480pxです。
- 各段階で主画面、ミッション、確認ダイアログ、通常タップ、CMからの復帰を確認します。主画面だけの成功で全体の下限を決めないでください。
- 動作する候補では、同じ操作を複数回繰り返し、数分程度の継続も確かめます。画素の配置次第で低い解像度の方が一致する場合もあるため、一度の不一致から下限を決めません。
- 「正常と記録した幅へ戻す」は、その端末設定で、現在の全画面を手動で正常と記録した時の実際の幅を復元します。復元後も「開き直す」が必要です。対象アプリや負荷設定を変えた場合は再評価してください。
- 問題が出たら「表示が崩れる」「認識できない」「タップが合わない・届かない」「起動できない」をアプリ別に記録します。

試験版で選べる最小幅は32pxです。これは実装した実験範囲の端であり、Android・端末・ゲームが実用的に動く下限を示す数字ではありません。

## 記録に入るもの

「実験記録を見る・コピー」から直近80件の起動記録を取り出せます。合否を付ける前の起動も `UNASSESSED` として残ります。

- 対象アプリ、APK版、端末設定、開始日時、実際の幅・高さ・DPI、指定幅、画面数、開始時の負荷設定。
- 手動評価と、評価時の状態・画像の古さ・入力完了回数・画像取得エラー・起動エラー。
- 同じ起動で画像判定が実行されていた場合は、直近の主画面判定・判定時間・判定画像の古さ。
- 評価時点の本アプリのJavaヒープ使用量と、端末全体の空きメモリの瞬間値。

入力完了回数はAndroidへの送信完了です。ゲームの応答成功や報酬取得の回数ではありません。合否は利用者が画面を見て付ける評価です。`homeRecognized` はその瞬間の主画面判定なので、ミッションやCM中に false でも直ちに認識失敗を意味しません。

`imageArraysBytesEstimate` は幅×高さ×4バイト×2配列×画面数の理論量です。共有ワークスペース・画像バッファ・GPU・ゲーム本体などを含む総メモリ量ではありません。空きメモリの差も、バックグラウンド処理やキャッシュの影響を受け、解像度変更だけによる節約量とは断定できません。

## 録画画像による予備試験

同梱の `resolution-replay-v1.109.csv` は、既存の録画画像を各幅の整数画素配列へ縮小してから、出荷する認識処理に入力した結果です。実機でその解像度を指定してゲームを起動した実験ではありません。

対象は増えうさぎの「ゲット」9場面と、農園の「閉じる／このままはじめる」6場面の計15場面です。画素の認識と操作点が期待するボタン内にあるかを調べています。実際のタップ送信・ゲーム進行・CM復帰はこの試験の対象外です。

| 幅 | 増えうさぎ | 農園 |
|---:|---:|---:|
| 720〜320pxの各選択幅 | 9/9 | 6/6 |
| 280px | 9/9 | 3/6 |
| 240px | 9/9 | 6/6 |
| 200px | 9/9 | 6/6 |
| 160px | 9/9 | 0/6 |
| 128〜32pxの各選択幅 | 0/9 | 0/6 |

この15場面から「200pxで全ゲームを自律操作できる」とは判断できません。実際に低解像度で起動するとアプリ側のレイアウト・描画・広告が変わる可能性があり、端末での確認が必要です。

## 設計と検証の範囲

幅・DPI・メモリ予算の計算、低解像度を受け取る実行部、プレビューから実際の画素への座標変換をJVMで検証します。通常設定は従来の計算に戻ります。明示した幅が画像用メモリ予算を超える場合は、別の幅へ黙って変更せず起動を拒否します。

停止・再作成で世代を変え、古い画像や遅れて届いた入力処理を新しい画面に流用しません。「開き直す」は旧画面の解放処理完了を待ち、最大5秒で確認できなければ新しい画面の作成を止めます。実行中の画面をリサイズし続ける方式ではありません。

PC表示中の端末側の実験再作成は無効です。この環境にAndroid端末は接続されていないため、Android 17 / Pixel 10、F-52Aでの低解像度起動と動作下限は未確認です。保存・コピー・画面再作成のAndroid UI実操作も未確認です。

- [DisplayManager.createVirtualDisplay：幅・高さ・densityDpiの指定](https://developer.android.com/reference/android/hardware/display/DisplayManager)
- [画面密度とdp・pxの関係](https://developer.android.com/training/multiscreen/screendensities)

APKの更新・署名確認・JVM検証の結果は同梱の `VALIDATION-v1.109.json` とログを参照してください。
