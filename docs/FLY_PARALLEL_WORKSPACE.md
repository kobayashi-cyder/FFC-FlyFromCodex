# v7.9: conversation, documents and development workspace

- Up to 256 logical conversations; create 16/32/64 at once from the header. The pool stays lazy: empty conversations do not allocate workers.
- Default two, maximum four worker slots. Code, document and reading bodies reuse the bounded existing IR/quality implementations inside real Web Workers. They compile a connectome per worker job and receive a circuit snapshot. Main-thread topology selection controls tool execution, routing among close context matches, and queued-job selection. This is parallel body execution, not parallel execution of the main graph's shared scratch buffers. Worker count increases RAM; process RSS on Android is not measured.
- Per-conversation FIFO and one active task per conversation; maximum 256 queued jobs, 16 queued jobs per conversation. Different conversations overlap. Video jobs hold a shared lane until native MP4 completion; DOM tools serialize. Pending/status/error output is visible. Background completion does not switch the foreground conversation.
- Header mode toggle, conversation batch creation and concurrency controls have 44px touch targets. Settings now contain only local-model/A1111 connection, bounded video quality, voice and display settings. Historic UI headings/notes are removed from the internal compatibility body. Required DOM bodies remain hidden and inert because the existing renderers reference them; generation/output actions are absent from the settings navigation.
- Normal chat cannot be hijacked by an acquired unrelated action. Private thread memory replaces the former shared CHAT context during chat composition. Personal names are processed before generic word learning. Regular chat does not launch blocking Wikipedia calls; explicit research remains separate.
- Generated code/documents have inline edit, file save, static inspection and explicit DOCX share. Edits invalidate old validation and update the prior artifact for subsequent revision. Static inspection is not execution or unit testing. Unsupported local implementations fail their quality gate; successful template recipes are a limited procedural generator, not a general coding model.

## Optional local model

Settings → conversation/document/code model: enter a complete OpenAI-compatible URL such as `http://192.168.1.10:11434/v1/chat/completions` and an already-installed model name. Header online mode allows this connection. Installed PC models can run over LAN without internet; this still needs the PC and LAN. Phone-only offline mode never calls the model service. No weights or inference runtime are bundled in the APK, and no GPT-level ability is claimed. API authentication and streaming are not implemented.

The token/origin-guarded native bridge permits four simultaneous non-streaming requests, limits prompt/response sizes, and cancels on offline switch or Activity close. LAN/localhost HTTP is allowed; public hosts require HTTPS, redirects and URL credentials are rejected. Chat uses its conversation context; code/document drafts enter the worker's validation/repair/circuit output gates. Backend failure is shown rather than disguised as successful local generation.
