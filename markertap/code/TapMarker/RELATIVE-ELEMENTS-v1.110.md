# 相対位置の要素数と低解像度の成立条件

## 結論

**要素数だけで識別可能とは決められません。** 最初の設計候補は、対象ボタンを含む2要素で配置を候補化し、離れた3要素で配置の矛盾を確認する方法です。欠落への余裕を持たせるなら4〜6個の候補から整合する組を選びます。ただし、どの画面かを見分けるには、位置以外に形・色・文字・直前の状態が必要です。

実際に既存の学習処理を1〜6領域で比較したところ、幅320pxで識別できたのは17場面中13場面でした。6領域にしても全件にはなりませんでした。**現行の学習処理のまま、領域を増やすだけで全状態を扱う案は成立を確認できていません。**

v1.110のAPKは最小幅から上げる実験操作へ変更しています。今回比較した新しい領域の組を、そのままゲーム操作用のプリセットへ置き換えてはいません。

## 「要素」を何として数えるか

ここでの要素は、画面内の1つの画像領域です。例は見出し、対象ボタンのラベル、離れた固定アイコンです。1画素、RGBの3成分、同じ画像領域内の複数サンプルを別の目印とは数えません。

今回の実測は、既存の `ObservationLearner.signature` が選ぶ画像領域の個数を変えた比較です。意味上の独立した部品を自動発見した数ではありません。周辺背景を含む領域が選ばれることもあります。

## 推定：配置の決定と画面の識別を分ける

| 対応する目印 | 配置について分かること | 識別に残る問題 |
|---:|---|---|
| 1個 | 拡大率が既知なら移動量を求められる | 同じボタンや色塊が別画面にも出る |
| 2個 | 異なる2点なら移動・回転・同倍率拡大の候補を作れる | 2点の取り違え、同じ並びの別画面 |
| 3個 | 一直線上にない対応点なら一般のアフィン変換を決められる | 位置が一致してもGet／Playなどの意味は同じにならない |
| 4〜6個の候補 | 不一致・欠落に備え、整合する組を選べる | 全部一致を必須にすると、動く数字や消える要素で取りこぼす |

3個で生じる2点間の組は3組、4個なら6組ですが、これらは独立した6観測という意味ではありません。また、一列に並ぶ3個より、画面内で広がりを持つ3個の方が幾何の確認に向きます。

OpenCVは3対応点でアフィン変換、4対応点で透視変換を計算します。これは**対応点の組が正しいと分かっている場合の幾何の話**で、3点だけで任意のUIを識別できるという保証ではありません。[一次資料1](https://docs.opencv.org/4.x/da/d54/group__imgproc__transform.html)

点群の相対配置を特徴として使う考え方にはShape Contextsがありますが、対応する点の探索と外見の差も扱います。「位置だけ、一定個数だけで十分」という方法ではありません。[一次資料2](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2001/6435.html)

## 解像度の見積もり

現行の農園プリセットでは、「このままはじめる」の文字領域は画面高さの約1.9%です。1080×2424と同じ縦横比なら、起動幅をWとして文字領域の高さはおおむね `0.019 × 2424 / 1080 × W ≒ 0.0426W px` です。

| 起動幅 | この文字領域の高さの概算 |
|---:|---:|
| 32px | 1.4px |
| 64px | 2.7px |
| 128px | 5.5px |
| 160px | 6.8px |
| 200px | 8.5px |

例えば文字領域の高さが8px必要という**仮の条件**を置けば、必要幅は約188pxとなり、200px付近が試験候補になります。8pxは普遍的な認識限界でも測定済みの閾値でもありません。粗い色や図形で区別できる状態は、文字より低い解像度でも成立する可能性があります。

位置関係が保たれても、Get／Playや確認／キャンセルの違いを示す画素が消えた場合は、目印を増やしてもその情報を取り戻せません。認識後も、整数画素への丸めと位置推定の誤差を含め、実際の押下位置がボタン内に収まるかを別に確認します。

## 実測：1〜6領域の比較

学習用12画像と評価用24画像を分けました。評価画像は、正解の操作状態17画像（Get 9、Play 4、農園Close 2、農園Start 2）と、広告・主画面・別の報酬表示など7画像です。

既存の領域選択処理で各状態につき最大6領域を選び、先頭1〜6領域の全一致を比較しました。学習見本は既存の保存処理に合わせて幅192px以下、評価入力は元の保存画像から各幅へ補間して整数画素配列を作っています。閾値は既存の0.006のままです。評価画像から閾値や領域を調整し直してはいません。

| 幅 | 1領域 | 2領域 | 3領域 | 6領域 |
|---:|---:|---:|---:|---:|
| 32・48・64・96pxの各幅 | 0/17 | 0/17 | 0/17 | 0/17 |
| 128px | 4/17 | 4/17 | 0/17 | 0/17 |
| 160px | 11/17 | 11/17 | 11/17 | 11/17 |
| 200px | 11/17 | 11/17 | 11/17 | 11/17 |
| 240px | 11/17 | 5/17 | 5/17 | 5/17 |
| 280px | 13/17 | 13/17 | 13/17 | 13/17 |
| 320px | 13/17 | 13/17 | 13/17 | 13/17 |
| 720px | 13/17 | 13/17 | 11/17 | 11/17 |

各条件で、別状態との79比較に対する誤受理は今回0でした。操作対象付近を灰色で隠した17画像の人工的な欠落試験も、今回0件の受理でした。これは7枚の独立した未知画面を含む限定された素材での観測であり、実運用の誤認率が0という意味ではありません。画像は少数の録画から採っているため、場面間にも相関があります。

320pxで保留となった4枚はPlayです。領域を増やしても改善しませんでした。320pxで正解した13枚にはGet 9枚、Close 2枚、Start 2枚が含まれます。

元の専用プリセットによる15場面の試験と、この新しい学習領域の比較では、参照画像・対象場面・判定方法が違います。したがって「専用プリセットは200pxで15/15」「今回の汎用学習領域は200pxで11/17」は矛盾しません。

## 成立させる条件と判定

次の候補設計は、対象ボタン自身の認識を必須にし、見出しと離れた固定アイコンなどを補助に使う方法です。補助候補が増えても、無条件に全一致へ追加せず、同じ位置変換で説明できるか、別の状態の候補と競合しないかを確かめます。

初めに検証する要素数は「対象ボタン＋補助2個」の3個とします。ただし今回の比較は、この新しい合意判定方式の成功を証明していません。Playの見本・領域の安定性、画像の取り違えを先に修正し、別録画・隠れ・移動・再配置でも正解することが必要です。既に識別できる状態まで強い全一致で落とさないことも条件です。

今回判断できるのは、**最小幅から上げる実験は実装できるが、相対位置の領域数だけで全状態を通す案は現時点では合格にできない**というところです。Android実機での低解像度起動、画面認識、入力到達、ゲームの反応は未検証です。

再現用データは `relative-elements-v1.110.csv`、場面ごとの判定は `relative-element-details-v1.110.csv`、学習・評価の区分と選択領域は `relative-element-metadata-v1.110.txt` に保存しています。`tools/resolution-probe/run-relative.sh` で比較を再実行できます。
