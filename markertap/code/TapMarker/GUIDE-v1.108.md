# MarkerTap v1.108：2〜4アプリと進行エラーの通知

`jp.tapmarker.lite` / versionName `1.108` / versionCode `111`

## 更新と4アプリの選択

1. 旧版で「全停止」を押し、仮想画面を閉じます。
2. `MarkerTap-v1.108-four-apps.apk` を上書きインストールします。v1.107と同じ証明書で署名済みです。
3. ホームの「アプリを選んで画面を開く」、または操作パネルの「対象」を押します。
4. 「同時稼働数」で「4アプリ」を選び、「アプリを選択」を押します。
5. 対象アプリを4つ選択し、「配置方式へ」→「端末だけで仮想画面」へ進みます。接続済みなら既存の接続方式も利用できます。
6. 各画面の起動・表示確認後に自律を開始します。見出しプルダウンから各アプリの状態を確認し、「拡大」で映像を開けます。

3アプリを試す場合は手順4で「3アプリ」を選択します。保存した数は仮想画面数の上限で、選択した対象がそれより少なければ選択した対象だけを開きます。1アプリだけの選択も可能です。更新後の既定値は2で、既存の対象リストを切り詰めたり、勝手に別のアプリを追加したりしません。設定は次に画面を開くときへ適用し、現在動いている画面を設定変更だけで閉じません。

ホームにも保存した同時稼働数を表示します。対象数が上限を超えている場合は、端末の仮想画面の開始を止めて選び直しを案内します。PC表示と自由ウインドウの対象数は従来の扱いです。

## 取得・解析の負荷分散

- 起動をアプリごとに遅らせます。3・4画面では300msずつ、2画面では120msずつです。F-52Aの既存の650ms刻みを優先します。
- 稼働中の画像コピー間隔は、選択した処理プロファイルの間隔と `60ms × 実際の画面数` の大きい方を使います。4画面では最短240msです。画像の最初の取得後は各画面で時刻をずらし、遅れた取得をまとめて追いかけません。
- 初回の解析要求も画面ごとにずらします。その後は既存のアプリ別の実行ループと、1ワーカーの共有解析回路を使います。各アプリで実行中の要求を重複させない既存制御を維持します。
- アプリごとのImageReader・表示・入力先・オートマトンは維持します。見出しへ収納した画面も、自律中の画像取得を継続します。
- 既存の通常連打と強化操作の入力経路を維持します。今回のコピー間隔は通常連打の間隔を制限しません。
- 静止した画面の再取得は、既存の全画面共通キューで400ms以上の間隔を空けます。別アプリや古い世代の取得結果を受け入れません。

パネル内の一覧は端末の高さが許す範囲で4件分を表示し、小さい画面ではスクロールします。

## 進行エラーの通知とChatGPT Workへのコピー

ホームの「エラー通知の設定」からAndroidの通知を許可します。通知が未許可・無効の場合も、操作パネルの「進行エラーを見る」表示と診断文の保存は利用できます。通知の許可はAndroidの画面で行います。一度拒否して再要求できなくなった場合は、同じボタンから通知設定を開きます。

監視は1秒ごとに行い、入力やオートマトンの判断を変更しません。主な検出条件は以下です。

| コード | 検出条件 |
|---|---|
| FRAME_STALE | 認識に使える新しい元画像を取得できない状態が15秒以上継続 |
| ANALYSIS_SLOW | 元画像は新しいが、直近の画像判定が1500msを超える状態が15秒以上継続 |
| INPUT_REJECTED | 入力拒否・入力未確認が15秒以上継続 |
| INPUT_NO_PROGRESS | 主画面を認識し通常連打が必要なのに、入力完了回数が15秒以上増えない |
| BRANCH_CONFLICT | 複数の分岐条件が同時に成立する状態が8秒以上継続 |
| STATE_STALL | 主画面以外の同じ状態を通常120秒、広告状態では180秒以上継続して観測。登録された待機時間が長い場合はその時間＋30秒以上を優先 |
| START_FAILED / WINDOW_FAILED / LANE_STOP / STATE_MISSING | 起動失敗・画面作成失敗・異常理由による処理停止・状態の欠落を検出 |

正常な主画面への長時間滞在、CM中にタップしないこと、設定した長い待機、終了状態、手動の全停止だけを理由には通知しません。画像が取得・更新できなくなる場合はCM中でも診断対象です。同じ不調が続く間は重複通知を抑制し、同一アプリ・同一コードの通知は最低60秒空けます。

エラー時はパネルの表示かAndroid通知をタップし、「診断文をコピー」を押してChatGPT Workの入力欄へ貼り付けてください。通知を開いた時も、表示するのは発生時点に保存した診断文です。アプリを通じて自動送信はしません。

診断文には、発生日時、APK版、端末・OS、エラーコード、対象アプリ、状態名・ID、最後に完了したルール、直前に要求した操作と取得できる場合の座標、画像の古さ、判定時間、入力完了数、各仮想画面の状態、直近の処理・開始停止履歴を含めます。未取得の時刻情報は `-1` で示します。症状を記録するもので、根本原因や報酬加算の成否を断定しません。

最新5件の診断文を保持し、「過去のエラー」から個別にコピーできます。手動操作・全停止・正常復帰・アプリの再起動によって診断文を消しません。既読にするとパネルの通知表示を収納しますが、診断文は残ります。本体画面での自動操作は診断文を開くと停止し、仮想画面の自動操作は継続します。検出による自動停止・再起動の追加はありません。

## 検証範囲

APKのビルド、元v1.107との署名証明書一致、パッケージ名・バージョン、ZIP整合性と16KiB対応の整列を確認します。検証結果は `VALIDATION-v1.108.json` とログへ記録します。

新規 `VirtualLoadPolicyTest` は、2・3・4画面、異なる4つの負荷プロファイル、遅れた画像コールバック、収納中の取得継続、F-52Aの起動間隔、4画面の再取得順と取得先の分離を検証します。共有回路・古い画像・中止後の通知・ゲーム間の画素混在は既存のFrameCircuitTest等も併用します。新規 `ProgressWatchdogTest` は、一時的な取得遅延と継続的な不調の区別、CM・長時間待機、通常連打の未進行、4アプリの分離、停止・再開、検出後に内容が変わらないコピー用レポートを検証します。通常のcore回帰群も実行します。元ソースに録画fixtureのない旧full群4本は従来どおり対象外です。

この環境にはAndroid実機が接続されていません。端末のメモリ使用量、4アプリのCM再生と報酬加算、パネルの実際の描画・操作、Android通知・通知権限・クリップボードの実操作、再起動後の保存復元、長時間稼働は未確認です。4アプリを選択可能にする実装であり、端末の処理能力を保証するものではありません。画像の鮮度上限1500msは延長していません。判定にそれを超える時間がかかる場合は、古い画像を操作に使わず再取得します。

実機ではまず3アプリ、次に4アプリで、画像の古さ・入力完了回数・アプリの終了や再起動を比較してください。4アプリで取得遅延や停止が続く場合は、全停止後に同時稼働数と対象を2または3へ変更して開き直せます。

## 再ビルド

Java 17、Android API35、Build Tools35.0.0と既存の同梱依存を使います。

```bash
ANDROID_SDK_ROOT=/path/to/android-sdk \
TAPMARKER_KEYSTORE=/path/to/original-key.jks \
bash build.sh

ANDROID_SDK_ROOT=/path/to/android-sdk bash run-tests.sh
```

元の署名鍵はソースZIPに含めません。
