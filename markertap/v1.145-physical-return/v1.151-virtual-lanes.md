# MarkerTap v1.151 — virtual lane isolation / preview lifetime candidate

Status: **original-certificate signed v1.151 RC APK published and public-download SHA-256 verified; NOT device-tested / NOT promoted stable**. [Verified GitHub Actions run 41562962175](https://github.com/kobayashi-cyder/FFC-FlyFromCodex/actions/runs/41562962175).
Base: pinned public v1.150 signed APK, SHA-256 `58e6cd830350473dad218352b3e23f4efcb214b2624e1122823ceb1093345067`. The original v1.144 rebuild remains a separate option. Read `markertap/v1.145-physical-return/build.py` for strict SHA-256 input validation.

## Changes shipped in this candidate source
1. `VirtualFrameQueue` now holds up to **two in-flight screenshot requests** with one request per (generation, display ID). Global Android screenshot issue pacing remains 400ms. One callback can stall without blocking another display's **issuance** for the full original 2.5s timeout.
2. Late success/failure cannot finalize a removed or expired request; no image may be attributed to the other display or an earlier run generation.
3. A one-display removal clears only that display's queue entry. The existing backend-fatal policy remains intact: a genuinely removed virtual display still triggers the previous full-session safety stop. This change does not covertly relax owner-death cleanup.
4. `VirtualPreviewVisibilityBridge` transforms `View.GONE` into `View.INVISIBLE` when hiding the **phone-side** virtual preview. This retains measured view layout; it does not release or recreate the VirtualDisplay, ImageReader, input target or automation state. It is a mitigation experiment for the reported collapse/offline correlation, **not a verified network fix**.
5. The screenshot hardware-copy executor now has two workers and a **bounded capacity of two queued callbacks**. A hung copy worker cannot monopolize the other display's copy slot; overload fails closed instead of creating unbounded memory pressure.
6. The DEX integration patcher replaces the baseline `VirtualFrameQueue` (including `$Request`), redirects the virtual preview visibility call, and checks the original ABI and final bytecode against the exact overlay. It fails closed if the baseline methods or hooks differ.
7. `build.py`, `sign-release.py` and `release-local.py` have v1.151/versionCode154 and preserve the original update certificate and existing SHA safeguards.

- **Important limitation:** `displayListener.onDisplayRemoved` still invokes `backendLost()` for one removed display. Distinguish intentional removal and one-display loss from actual backend death in a separately reviewed, tested change.
- Preview `INVISIBLE` only retains the host view's layout. It does not prove the game's network session stays online after collapse. No release promotion until the actual game-side offline indicator and reward progress are tested on Pixel 10 / Android 17.

## Local signing and promotion gate (not executed without the original key)

`release-local.py` now calls the same `build-v151-from-v150.py` path that passed the full unsigned CI integration. `sign-release.py` refuses any unsigned input whose SHA-256 differs from the audited CI output `54cfccffa8bd6b5149fb2da563088b1cd3dde85037f567a33182308619d8befe`; this prevents silently signing a different APK. If a future approved source patch changes the APK, first run and audit a fresh unsigned integration, then update the pin in code and its test with the independently verified new digest.

In a **private, local environment only**, with the existing original keystore available outside the repository and outside the public output directory, run:

```bash
export MARKERTAP_STORE_PASSWORD='(enter privately; do not commit or log)'

  --baseline /private/MarkerTap-v1.150-integrated-signed.apk \

  --sdk tooling/sdk \

  --outdir /private/markertap-release-staging
```

## Two-stage release download gate (host code added; not executed on a real device)

`verify-release-download.py` provides a **preflight** (local signed APK + receipt + on-device logs) and a **published** audit (also downloads the exact asset from GitHub Release). It cannot generate a missing keystore or replace real Pixel 10 tests. Device logs must be independently inspected: a JSON claim of `pass` is not proof that the game progressed.

Keep all test logs, keystores, device identifiers, and the validation JSON in a **private local directory**, never in GitHub. The evidence JSON contains `signed_apk_sha256`, `package: jp.tapmarker.lite`, `version_code: 154`, `android_api: 37`, `device_model: Pixel 10`, `device_fingerprint`, and `cases`. Each case is `{"name":"...", "status":"pass", "evidence_file":"relative-private-log.txt", "evidence_sha256":"<actual log SHA256>"}`. Non-Pixel-10 Android 17 devices additionally need a written `equivalence_justification` (at least 30 characters). All eleven required case names are defined in `verify-release-download.py`: virtual 1/2-screen operation and collapse/restore, network online, advertisement recovery, continuous reward collection, memory/buffers, image freshness/generation, input isolation, and redundant tap prevention.

After actual device testing, in a **private local environment** run:

```bash
python3 verify-release-download.py \
  --stage preflight \
  --signed /private/MarkerTap-v1.151-integrated-signed.apk \
  --receipt /private/MarkerTap-v1.151-integrated-signed.validation.json \
  --device-evidence /private/markertap-device-tests/evidence.json \
  --sdk tooling/sdk
```

Only if the preflight passes **and independent device-log review is complete** may an operator publish the signed asset. After publication, run the same command with `--stage published`; it downloads `MarkerTap-v1.151-integrated-signed.apk` from `markertap-v1.151` in the official repository and verifies its SHA-256, package, versionCode, certificate, v2/v3 signatures, ZIP integrity, and 16 KiB alignment against the local signed receipt. **Do not change the README stable download before the published-stage gate passes.** The script does not upload, sign, publish, or update README.

CI exercises **eleven host-only negative/structure tests** for this gate. Those fixtures are explicitly synthetic, not evidence of an Android test.
